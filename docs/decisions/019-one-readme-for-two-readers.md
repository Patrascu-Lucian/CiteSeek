# 019 — One README for two readers

## Context

The README has two audiences with incompatible needs.

One arrives from a link, reads for about ninety seconds, and never runs the project. They want
to know what problem it solves, whether the hard part was actually solved, and whether the
person who built it can tell the difference between a measurement and a guess.

The other has cloned it and wants `pnpm install` to work. They want commands, environment
variables, and the traps — which database a `db:*` command actually hits, why the integration
suite needs a real Postgres.

Serving both in one file makes it long. The first reader has to scroll past nothing to reach
the story, but the second has to scroll past all of it to reach the commands.

## Options

**Split it.** `README.md` becomes the narrative and `docs/development.md` takes setup. Each
file has one audience and one voice, and the top of the README is entirely story.

The cost is drift. A second file that nobody reads while working is a file that stops being
true — and the setup instructions are exactly the content where being out of date is worse
than being absent, because a wrong command wastes an afternoon before it is disbelieved. This
project already carries `docs/strategy-plan.md`, which is _deliberately_ unmaintained and says
so; adding a second file that is accidentally unmaintained is a different thing.

**One file, ordered by audience.** Story, diagram, decisions, numbers, gaps — then getting
started, commands, testing, conventions. The reader who wants commands scrolls; the reader who
wants the story does not.

## Decision

One file, ordered by audience.

The deciding argument is not tidiness, it is which failure is recoverable. A long README that
is correct costs the second reader ten seconds of scrolling. A short README pointing at a
stale setup document costs them an afternoon, and they have no way to know which parts to
distrust.

## Consequences

**Length is the price**, and it is paid up front. The file is long enough that its structure
has to do real work: headings that say what is under them, and no section that exists only for
completeness.

**`## Numbers` is what justifies the length.** It is the section that could not be shortened
without becoming a claim rather than evidence — before-and-after figures, the method beside
each one, and the measurements that came out against the project's own expectations. A reader
skimming for whether this is a portfolio piece or a working system finds their answer there,
and it is the section most worth the scroll.

**Screenshots are committed rather than linked to a host.** They are regenerated by
`pnpm demo:shots` against a running instance, so the README shows the product as it is rather
than as it was when someone last remembered to update a hosted image.

**A stale README is a bug.** With no second file to blame, anything wrong here is wrong in the
one place everyone reads. The test counts and the milestone line are the parts that rot
fastest, and both are checked when a milestone closes.
